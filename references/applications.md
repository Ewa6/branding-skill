# Test the identity in real use

Moodboards establish intent; applications expose whether it holds. Choose representative surfaces from the brief rather than implementing an entire product.

## Controlled specimens

Use identical realistic content across variations. Keep approved identity and hard constraints fixed while changing the variable under discussion. Mark the test layout as a vehicle, not a selected final layout.

For an accumulative or user-populated product, show empty, partial and full states. Add long names/rewards, typical and maximum text, optional pictures/themes and relevant language differences. Check the visual result as well as fit.

NieZamulaj's useful comparison contained six states: empty/12-of-30/full, plain and with an optional accent. It revealed that repeated ticks and “done” labels added noise. Task-only labels, explicit short titles and a balanced two-line reward were stronger. The generic lesson is to test accumulated content, not to copy those exact mechanics.

## Components

Extract reusable anatomy only after a real-use pass: image slots, number tabs, fields, rewards, headings, list rows, controls or state messages relevant to this product. Record dimensions/tokens, content limits, behavior implied, allowed variants and examples. Keep components precise enough to reuse without pretending study code is production UI.

## Quiet states and cross-channel behavior

Prepare relevant first-use, empty, missing-image, long-content and failure states. A beautiful celebratory screen does not establish a useful error state. Verify wording against actual capabilities.

Show how the identity translates to mobile and desktop without forcing paper proportions onto a screen. If future motion is requested, record purpose, location, reduced-motion handling and implementation stage. Do not implement it early merely to decorate the brand specimen.

## Review

Use actual browser and PDF renders. Check loading, overflow, reading order, practical type size and source asset fidelity. When peer review changes a layout, rerun affected checks on the corrected output.

Conclude with findings: what the application taught, which components changed, what remains a proposal, and what is now ready for final design. Do not claim user testing from a simulated viewer or imply app features were built by drawing them.
